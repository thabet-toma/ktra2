## 0. بيئة القياس — وهي تحدّ من تعميم النتائج

| العنصر | ما كان فعلاً |
|---|---|
| **العتاد** | نواة معالج **واحدة** · 3.8GB ذاكرة · Ubuntu 24.04 |
| **قاعدة البيانات** | MySQL 8.4.11 — قاعدة `ktra_loadtest` **معزولة** على نفس خادم MySQL |
| **التطبيق تحت الاختبار** | gunicorn **3 sync workers**، `--timeout 180`، على `127.0.0.1:8001` — مطابق لإعداد الإنتاج القائم |

| **الإنتاج أثناء القياس** | على المنفذ 8000 وقاعدته **لم تُمسّ**؛ بقي يردّ **200** طوال القياس (60–265ms) |

### ⚠️ التحفّظ الإلزامي — اقرأه قبل أي استشهاد بالأرقام

**locust زاحم gunicorn وMySQL على النواة الواحدة نفسها**، وخادم الإنتاج كان يخدم
مستخدمين حقيقيين بالتوازي على المنفذ 8000. أي أن مولّد الحمل والتطبيق والقاعدة
وحملَ الإنتاج الحقيقي تقاسموا كلهم معالجاً واحداً.

**الأرقام أدناه تصف هذا النشر بهذا العتاد — لا سقف الكود على عتاد مخصّص.**
أي جملة من نوع «النظام يتحمّل N مستخدماً» بلا ذكر العتاد تحريفٌ لهذا القياس.

## 1. تجهيز البيئة (مرة واحدة)

### 1.1 قاعدة بيانات معزولة

```bash
mysql -u root -p -e "CREATE DATABASE ktra_loadtest CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root -p -e "CREATE USER 'ktra_load'@'localhost' IDENTIFIED BY '<pw>'; \
                     GRANT ALL ON ktra_loadtest.* TO 'ktra_load'@'localhost';"
```

اسم القاعدة **يجب** أن يحوي `loadtest` — أمر البذر يرفض العمل بدونه (انظر §1.3).

بيئة التطبيق (ملف `.env` منفصل، لا تعديل على إعدادات الإنتاج):

```bash
export MYSQL_DATABASE=ktra_loadtest MYSQL_USER=ktra_load \
       MYSQL_PASSWORD='<pw>' MYSQL_HOST=127.0.0.1 MYSQL_PORT=3306
python manage.py migrate
```

> ### 🔴 تصحيح عاجل (2026-08-12) — أسماء المتغيّرات كانت خاطئة هنا
> كانت هذه الفقرة تكتب `DB_NAME` و`DB_USER` و`DB_PASSWORD` و`DB_HOST`، بينما
> `core/settings.py` لا يقرأ إلا `MYSQL_DATABASE` و`MYSQL_USER` و`MYSQL_PASSWORD`
> و`MYSQL_HOST` و`MYSQL_PORT`.
>
> **الخطر لم يكن فشلاً بل نجاحاً في المكان الخطأ:** المتغيّرات الخاطئة **تُتجاهَل
> بصمت** فيبقى `.env` سارياً — أي أن من نسخ الأوامر حرفياً كان **يبذر آلاف
> الفواتير على قاعدة الإنتاج** وهو يظنّها معزولة. لا رسالة خطأ ولا تحذير.
> الحاجز الوحيد الذي كان سيمنع الكارثة هو حارس `--expect-db` في أمر البذر —
> وهو حاجز أخير لا أول.

### 1.2 اعتماديات مولّد الحمل (منفصلة عن الإنتاج)

```bash
python -m venv .venv-load
. .venv-load/bin/activate
pip install -r load_tests/requirements.txt      # locust==2.46.0
```

`load_tests/requirements.txt` منفصل عن `requirements.txt` الإنتاجي عمداً — لا يُثبَّت locust ولا gevent على الخادم.
النسخة 2.46.0 هي **آخر إصدار مستقر يقبل Python 3.10** (سقف السيرفر): 2.46.1 فما فوق يشترط `>=3.11` (مصدر التحقق: `https://pypi.org/pypi/locust/json`).

### 1.3 بذر بيانات بحجم واقعي

```bash
python manage.py seed_load_test_data --i-know-what-im-doing \
    --password '<كلمة مرور حسابات الحمل>' \
    --tenants 4 --products 800 --customers 200 --suppliers 40 \
    --invoices 1500 --days 540 --post-ratio 0.85 \
    --expect-db ktra_loadtest \
    --manifest load_tests/seed_manifest.json
```

يولّد لكل شركة: شجرة حسابات + فترات مالية + مستودع + ضريبة مخرجات 16% + أصنافاً برصيد افتتاحي حقيقي + عملاء وموردين + آلاف فواتير البيع **المرحّلة** (قيود وحركات مخزون فعلية). كل الكتابة تمرّ بمسارات النظام (`heal_company_seed`، `record_stock_movement`، `post_sales_invoice`، `next_invoice_number`) فما يُبذَر يطابق ما ينتجه النظام.

**حارس السلامة (5 طبقات، تسبق أي كتابة ويفشل مغلقاً):**

1. `--i-know-what-im-doing` إلزامي.
2. اسم القاعدة يحوي `loadtest`/`load_test`، أو يطابق `--expect-db` حرفياً.
3. **لا شركة في القاعدة خارج بادئة `LOADTEST`** — وجود شركة حقيقية واحدة يوقف الأمر.
4. **لا مستخدم غير مستخدمي الحمل** (عدا السوبر أدمن).
5. مضيف القاعدة محلي، إلا مع `--allow-remote-db` صراحةً. وSQLite مرفوضة إلا مع `--allow-sqlite` (أرقامها لا تمثّل الإنتاج).

الطبقتان 3 و4 هما الحارس الحقيقي: العَلَم يُنسى، أما قاعدةٌ فيها بيانات مستخدمين فتُوقف الأمر مهما بلغت الأعلام.

> **ملاحظة على الطبقة 3 (§5.2):** كانت ترفض **كل قاعدة نظيفة** لأن هجرات Django
> تُنشئ «Default Company». **أُصلح 2026-08-12** — والطبقة ما زالت ترفض أي شركة
> حقيقية.

كلمة المرور تُمرَّر في سطر الأوامر ولا تُكتب في أي ملف — البيان (`seed_manifest.json`) يحمل معرّفات وبُرداً فقط، بلا أسرار.

### 1.5 تشغيل الخادم كما في الإنتاج

```bash
gunicorn core.wsgi:application \
    --bind 127.0.0.1:8001 \
    --workers 3 \
    --timeout 180 \
    --access-logfile - --error-logfile -
```

هذا هو **إعداد الإنتاج القائم** (3 sync workers)، وهو ما قِيس. البديل
(`gthread`) قِيس أيضاً كمقارنة مستقلة — النتيجة في §3.5، وهي **ليست في صالحه**
على هذا العتاد.

## 2. تشغيل التدرّج 50 → 150 → 300 → 500

```bash
export KTRA_LOADTEST_PASSWORD='<نفس كلمة مرور البذر>'
export KTRA_LOADTEST_MANIFEST=load_tests/seed_manifest.json

for U in 50 150 300 500; do
  locust -f load_tests/locustfile.py \
      --host http://127.0.0.1:8001 \
      --users "$U" --spawn-rate "$((U / 10))" --run-time 3m --headless \
      --csv "load_tests/results/run_${U}" --html "load_tests/results/run_${U}.html"
  sleep 120   # تهدئة بين المستويات كي لا يتداخل ذيل مستوى بأوّل الذي يليه
done
```

**الخليط المرجّح في `load_tests/locustfile.py`** (مطابق لبرومت المرحلة 6):

| الوزن | السلوك | النقاط الفعلية |
|---|---|---|
| 40% | فتح قوائم | `/api/sales/invoices/?page` · `/api/inventory/products/?page` · `/api/partners/?page` · `/api/accounting/journals/?page` · `/api/inventory/stock-movements/?page` · `/api/logistics/purchase-invoices/?page` |
| 25% | تفاصيل مستند | `/api/sales/invoices/{id}/` (وجزء منها فحص عزل — أدناه) |
| 15% | إنشاء فاتورة بيع كاملة | `POST /api/sales/invoices/` (2-5 بنود) ثم `POST /api/sales/invoices/{id}/post/` |
| 10% | تقرير | `/api/reports/{sales-summary\|sales-by-customer\|sales-invoices\|receivables-aging\|payables-aging\|stock-valuation\|customer-balances}/` |
| 10% | بحث/autocomplete | `/api/inventory/products/?view=lookup&search=` · `/api/partners/lookup/?search=` |

**تفاصيل تعاقدية روعِيَت في السيناريو:**

- **العزل عبر `X-Tenant-Id`:** كل مستخدم افتراضي مربوط بشركة واحدة طوال حياته، وموزَّع بالتناوب على 3-5 شركات. `core/tenant_utils.py` لا يستنتج الشركة إلا حين تكون وحيدة في القاعدة — وهو ما لا يصحّ هنا عمداً.
- **الترقيم إلزامي بعد P0-5:** قوائم الفئة أ على `EnforcedPageNumberPagination`؛ كل طلب قائمة يمرّر `?page=&page_size=`. طلبات الـautocomplete وحدها بلا ترقيم لأنها المسار الفعلي للمحدِّدات (`view=lookup` / `lookup/`).
- **حدّ محاولات الدخول (P0-13):** `hr/auth_api.py` يحدّ 10 إخفاقات لكل بريد/IP كل 15 دقيقة. لذلك **التوكن يُجلَب مرة واحدة لكل حساب ويُشارَك** بين كل المستخدمين الافتراضيين عليه — 500 مستخدم افتراضي = 3-5 عمليات دخول لا 500.
- **حدود الخطة:** شركات البذر على خطة `Enterprise` (بلا حدود، `core/plans.py`) — وإلا رُفضت فواتير الحمل بـ«تجاوزت حدّ الخطة» فبدا الرفض خطأ أداء.

**فحص العزل تحت الحمل (لا الأداء وحده):** نسبة `KTRA_LOADTEST_ISOLATION_RATIO` (افتراضياً 10%) من طلبات التفاصيل تستهدف **مستند شركة أخرى** بتوكن شركةٍ أخرى. الردّ المقبول 403/404؛ أي `200` يُسجَّل فشلاً باسم `[isolation]` في تقرير locust. أي رقم غير صفر في هذا السطر = خرق عزل تحت التزامن ويسبق كل نقاش أداء.

|---|---|---|---|---|---|---|---|

| **150** | 2,034 | 0 | 0.00% | 8,200ms | **11,000ms** | 11,000ms | 13.6 ط/ث |

**الإجمالي: 8,566 طلباً، حالة فشل واحدة.**

### 3.2 الحكم مقابل عتبة النجاح

**العتبة المعلَنة:** عند 500 مستخدم متزامن ⇒ p95 < 2,000ms ومعدل أخطاء < 1%.

> ## ❌ فشل عند 500 مستخدم
> **p95 = 29,000ms — أي 14.5 ضعف العتبة.** معدل الأخطاء وحده اجتاز (0.00%)،
> والعتبة تشترط الأمرين معاً.

**عند أي مستوى بدأ التدهور: بين 50 و150.**

| المستوى | p95 | معدل الفشل | الحكم |
|---|---|---|---|
| **50** | 1,600ms | 0.05% | ✅ **ناجح** — ضمن العتبتين كلتيهما |
| **150** | 11,000ms | 0.00% | ❌ فاشل — p95 تجاوز العتبة بـ5.5 أضعاف |
| **300** | 19,000ms | 0.00% | ❌ فاشل |
| **500** | 29,000ms | 0.00% | ❌ فاشل |

**السعة العملية لهذا النشر ≈ 50 مستخدماً متزامناً.** لا نملك قياساً بين 50 و150،
فالحدّ الدقيق للانكسار داخل هذا المدى **غير معروف** — المعروف أن 50 يمرّ و150 لا.

**خروقات العزل:** لم يُسجَّل في البيانات الملتقطة تصنيفٌ لحالة الفشل الواحدة عند
المستوى 50، فلا يصحّ إعلان «صفر خرق». المؤكَّد أن مجموع كل الإخفاقات على
المستويات الأربعة **حالة واحدة من 8,566**، أي أن أقصى ما يمكن أن يكون خرقاً هو
طلب واحد. تحديد هويّتها يحتاج مراجعة `run_50_failures.csv` — وهي الخطوة الوحيدة
المتبقية قبل الجزم بصفر.

### 3.3 التحليل — أهم رقم في التقرير ليس زمن الاستجابة

**الإنتاجية ثابتة عند 13.6–16.9 طلب/ثانية في المستويات الأربعة كلها.**

عشرة أضعاف المستخدمين (50 ← 500) وبنفس الإنتاجية. هذه **بصمة الإشباع الكامل**:
المستخدمون الإضافيون لا يُنتجون عملاً أكثر، بل **طابوراً أطول**. زمن الاستجابة
يتضاعف لأن الطلب ينتظر دوره، لا لأن معالجته صارت أبطأ.

**والرقم يفسّر نفسه حسابياً:**

```
3 workers ÷ ~0.2 ثانية زمن خدمة = 15 طلب/ثانية
```

القياس أعطى 13.6–16.9. **السقف هو `عدد الـworkers ÷ زمن الخدمة`، لا شيء آخر.**

**وصفر أخطاء عند 150 و300 و500** — النظام **لا ينهار تحت الضغط، بل يبطئ فقط**.
لا انقطاع اتصال، ولا 500، ولا انتهاء مهلة (`--timeout 180` لم يُلمس: أسوأ p99
كان 29 ثانية). سلوكٌ جيد يستحق التسجيل: التدهور رشيق لا كارثي.

### 3.4 أبطأ النقاط — تُقرأ عند 50 لا عند 500

**عند 500 كل النقاط تُظهر p50 = 26,000ms وp95 = 29,000ms بالتساوي التام** —
تقريرٌ ثقيل ونقطةٌ بسيطة وترحيلُ فاتورة: نفس الرقم بالضبط. الطابور يبتلع الجميع،
فجدول «أبطأ 10 نقاط» عند الإشباع **بلا معنى تشخيصي**: هو يقيس طول الطابور لا كلفة
النقطة.

الكلفة الحقيقية لكل نقطة تظهر عند 50 (قبل الإشباع):

| النقطة | p50 | p95 |
|---|---|---|
| `GET /api/reports/payables-aging/` | 610ms | **2,100ms** |
| `POST /api/sales/invoices/{id}/post/` | 830ms | 1,700ms |
| `GET /api/inventory/products/?page` | 580ms | 1,600ms |
| `GET /api/inventory/products/?view=lookup&search` | 580ms | 1,600ms |
| `GET /api/reports/sales-summary/` | 440ms | 1,600ms |
| `GET /api/sales/invoices/?page` | 620ms | 1,600ms |
| `GET /api/accounting/journals/?page` | 610ms | 1,500ms |
| `GET /api/inventory/stock-movements/?page` | 620ms | 1,500ms |
| `GET /api/partners/lookup/?search` | 390ms | 1,500ms |
| `GET /api/reports/sales-by-customer/` | 550ms | 1,500ms |

**قراءة الجدول:** الفارق بين أبطأ نقطة (2,100ms) وأسرعها (1,500ms) **600ms
فقط** — أي أن التباين بين النقاط هامشي مقارنةً بمستواها المشترك. لا نقطة شاذّة
تسحب المجموعة، وأثقلها (`payables-aging`، وهو البند P0-9 المُصلَح) تحت
2.2 ثانية على قاعدة أكبر من الإنتاج.

### 3.5 نموذج العامل: `sync` مقابل `gthread`

نفس المستوى (150) ونفس البيانات، على نسخة الاختبار وحدها:

| النموذج | طلبات | فشل | p50 | p95 | الإنتاجية |
|---|---|---|---|---|---|
| `sync` 3 workers | 2,034 | **0** | 8,200ms | **11,000ms** | **13.6** ط/ث |
| `gthread` 3×4 | 1,891 | **40** | 7,700ms | 14,000ms | 12.6 ط/ث |

**`gthread` أسوأ في كل عمود عدا p50 على نواة واحدة:** أخطاء حيث لا أخطاء
(40 مقابل صفر)، وp95 أعلى، وإنتاجية أقل. الشرح المباشر: 12 خيطاً على نواة واحدة
تعني تبديل سياق أكثر بلا أي توازٍ حقيقي مقابله.

> **قرار مسنود بالقياس: يبقى `sync` على هذا العتاد.** يُعاد تقييم `gthread` على
> عتاد متعدد الأنوية فقط — حيث الخيوط تجد ما تشغله فعلاً. وهذا يصحّح ضمناً
> التوصية القديمة في هذا الملف نفسه (`gthread` بـ`workers=2×cores+1`): كانت
> استنتاجاً معقولاً قبل القياس، ونقضه القياس على هذه البيئة.

## 4. قرار Celery

> ## 🟢 الحكم: **Celery غير مطلوب للحمل المقيس.**
> **والاختناق ليس عملاً ثقيلاً داخل الطلب — بل سعة.**

### 4.1 الدليل (ثلاث نقاط، كلها من القياس)

**1. لا نقطة تلامس عتبة القرار.** برومت المرحلة 6 يشترط للنقل إلى Celery وجود
نقاط تتجاوز **3–5 ثوانٍ** بسبب عمل ثقيل داخل دورة الطلب. عند 50 (قبل الإشباع،
حيث تُقرأ الكلفة الحقيقية) **أبطأ نقطة على الإطلاق 2.1 ثانية** — دون العتبة
الدنيا. وقاعدة القرار المكتوبة في هذا الملف تقول حرفياً: p95 < 3s على كل
المرشّحين ⇒ يُوثَّق «Celery غير مطلوب عند هذا الحجم».

**2. التساوي التام عند 500 يُثبت أن الانتظار في الطابور لا في التنفيذ.** حين
يُظهر تقريرٌ ثقيل ونقطةُ تفاصيل بسيطة **نفس** p50 ونفس p95 بالضبط، فالزمن
المقيس ليس زمن العمل. لو كانت نقطةٌ ثقيلة هي السبب لتفاوتت الأرقام — وهي لم
تتفاوت.

**3. السقف يساوي `workers ÷ زمن الخدمة` حسابياً وقياسياً.** ونقل العمل إلى مهام
خلفية **لا يرفع هذا السقف**: الطلب سيظل يحتاج worker ليردّ، والـworkers ثلاثة.
Celery يُقصّر زمن الخدمة لنقطةٍ بعينها، لكن لا نقطة هنا طويلة أصلاً — فما يُنقل
لا يوفّر شيئاً يُذكر، ويُدفع ثمنه وسيطَ رسائل مُداراً في الإنتاج (§4.4).

### 4.2 ما يرفع السعة فعلاً — مرتّباً بالأثر

| # | الإجراء | لماذا |
|---|---|---|
| 1 | **أنوية أكثر** ⇐ `workers = cores × 2 + 1` | السقف = workers ÷ زمن الخدمة. زيادة الـworkers على نواة واحدة تزاحم لا تُنتج؛ الأنوية هي القيد الحقيقي |
| 2 | **`REDIS_URL`** | الكاش والـthrottle الحاليان على **ملفات بلا قفل بين العمليات** — كل worker يتنازع على نفس الملفات. هذا يُقصّر زمن الخدمة، فيرفع السقف من البسط والمقام معاً |
| 3 | إعادة تقييم `gthread` | **بعد** توفّر الأنوية فقط — على نواة واحدة قِيس فوجِد أسوأ (§3.5) |

**لا شيء من هذه الثلاثة يتطلّب Celery.**

### 4.3 ⚠️ ما لم يُقَس — لا تدّعِ أن القياس حسمه

`P1-12` (ترحيل دفعي لفواتير الشحنة) و`P1-13` (تنازع أقفال
`_recompute_product_stock`) **لم يستهدفهما هذا السيناريو**:

- `load_tests/locustfile.py` يرحّل فاتورة **واحدة** كل مرة — لا دفعة شحنة فيها
  مئات الفواتير داخل `transaction.atomic` واحدة. فالحالة التي يصفها P1-12 لم
  تُشغَّل أصلاً.
- ولا يُجبر السيناريو مستخدمَين متزامنَين على **نفس الصنف الشائع**، وهو الشرط
  الوحيد الذي يُظهر تنازع أقفال `select_for_update` في P1-13. الأصناف موزَّعة،
  فالتنازع لم يقع.

> **قرار P1-12 وP1-13 يبقى معلّقاً.** إغلاقهما بالاستنتاج من هذا القياس خطأ
> منهجي: غياب العَرَض من سيناريو لا يستهدفه ليس دليل غياب العلّة. يحتاجان
> سيناريو مستهدِفاً (دفعة شحنة حقيقية + تزاحم مقصود على صنف واحد)، وحينها فقط
> يُحسم قرارهما.

وأربعة مرشّحين آخرين من `docs/SCALABILITY_AUDIT.md §6` **خارج الخليط بطبيعتهم**
ولم يُقاسوا: رفع Cloudinary المتزامن (`core/media_views.py`)، وتقرير Landed Cost،
وإقفال السنة، وإعادة مطابقة COGS والجرد. الأربعة عمليات دفعية أو خارجية يقيسها
سيناريو مستقل لا خليط المستخدم العادي.

### 4.4 تبعية مسبقة (لو عاد القرار يوماً)

Celery يفترض وسيطاً (Redis غالباً). البند P0-6 (استبدال `FileBasedCache`) موسوم
منفَّذاً، لكن التشغيل الفعلي على الخادم المشترك **بلا Redis** يجعل هذه التبعية
جزءاً من كلفة القرار لا هامشاً منه: أي «نعم لـCelery» يعني أولاً وسيط رسائل
مُدارٌ في الإنتاج — وهو نفسه البند رقم 2 في §4.2، ويستحقّ التنفيذ لذاته قبل
Celery وبمعزل عنه.

### 5.1 ✅ لا يمكن إعادة بناء قاعدة البيانات من الهجرات — الأخطر *(أُصلح)*

`core/models.py` → `SystemAttachment` معرَّف بـ**`managed = False`**، وهو
**النموذج الوحيد كذلك في المشروع كله** (فُحص: لا `managed = False` في أي app
أخرى). النتيجة أن Django:

1. يُسجّل `core.0001_initial` كمطبَّقة `[X]`، **و**
2. **لا يُنشئ جدول `system_attachments` إطلاقاً** — النموذج غير مُدار فلا DDL له.

**أُثبت عملياً:** قاعدة جديدة بعد `migrate` كامل — الهجرة معلَّمة مطبَّقة والجدول
غير موجود. وأي عملية تلمسه تنفجر بـ`(1146) Table doesn't exist`. **هكذا اكتُشف:**
حذفٌ تعاقبي انفجر أثناء تجهيز قاعدة الحمل.

الإنتاج يملك الجدول لأنه أُنشئ **يدوياً خارج Django** في وقتٍ ما.

**الأثر:** تعافٍ من كارثة، أو بيئة تجريبية، أو خادم جديد ⇒ **مخطط ناقص**.
الاستعادة من `mysqldump` تنجح (تحمل الجدول معها)، لكن **`migrate` وحده لا يكفي** —
وهذا غير موثّق في أي مكان، فمن يبني من الهجرات يظنّ نفسه انتهى.

هذه **بقيّة** فئة عطل عولجت سابقاً: نماذج `chartofaccounts`/`partners`/`tenants`
كانت بنفس العلّة وقُلبت إلى `managed = True`؛ سقط `SystemAttachment` من تلك
الكنسة.

#### ✅ الإصلاح (بإذن المالك، 2026-08-12) — وعطلٌ ثانٍ كان مختبئاً تحته

`managed = True` في `core/models.py` و`core/migrations/0001_initial.py` معاً — نفس
النمط المطبَّق سلفاً على `partners` و`tenants`. آمن على الإنتاج: الهجرة مسجَّلة في
`django_migrations` فلا تُنفَّذ ثانيةً، والأثر محصور في البناء من صفر.

**لكن القلب وحده كان سيُنتج جدولاً خاطئاً.** حقل `tenant` (FK إلى `Tenant`) موجود
في النموذج منذ البداية و**غائب عن `CreateModel` تماماً** — لأن مُكتشِف الهجرات
**يتجاهل حقول النماذج غير المُدارة** فلم يُسجّله قطّ. أي أن `managed = True` بلا
إضافة الحقل كان سيبني `system_attachments` **بلا عمود `TenantID`** — وهو عطل أسوأ
من الأصل لأنه يبدو ناجحاً. أُضيف الحقل في نفس الهجرة.

**التحقق لم يكن باختبارات SQLite** (لا تحرس المخطط — انظر §5.4)، بل بـ`migrate`
كامل على قاعدة **MySQL 8.0 فارغة**:

```
table exists: True
AttachmentID int NOT NULL PRI · TenantID int NOT NULL MUL · RelatedTable varchar(50)
RelatedID int · FileType varchar(50) NULL · FilePath varchar(500) · UploadedAt datetime(6)
FK: system_attachments_TenantID_a7241d19_fk_tenants_TenantID → tenants
```

**أثر جانبي مفيد:** الجدول لم يكن يُنشأ في قاعدة الاختبار أصلاً (`run_syncdb`
يتخطّى النماذج غير المُدارة)، أي أن النموذج كان **خارج تغطية الاختبارات كلياً**.
صار يُنشأ الآن، والمجموعة خضراء بعده.

### 5.2 ✅ حارس البذر يرفض كل قاعدة نظيفة *(أُصلح)*

`tenants/management/commands/seed_load_test_data.py` يرفض القاعدة إن وجد شركة لم
يصنعها هو:

```python
Tenant.objects.exclude(CompanyName__startswith=COMPANY_PREFIX)
```

لكن هجرات Django نفسها تُنشئ شركة اسمها **«Default Company»**
(`tenants/migrations/0005_backfill_default_company.py`) — فكل قاعدة اختبار جديدة
**مرفوضة بالتعريف**. القاعدة النظيفة هي بالضبط الحالة التي بُني الحارس ليسمح بها.

لم يظهر العطل قبل اليوم لأن **العدّة بُنيت ولم تُشغَّل قطّ**.

تُجووزت يدوياً أثناء القياس (بحذفها من القاعدة المعزولة) التزاماً بقيد البرومت.

#### ✅ الإصلاح (بإذن المالك، 2026-08-12)

استثناء `DEFAULT_TENANT_NAME` وحدها في الطبقة 3 — لا عَلَم جديد، لأن الشركة
الافتراضية ليست بيانات مستخدمين فلا يحمي وجودُها شيئاً.

**تُحقّق موجباً وسالباً على قاعدة MySQL فعلية**، والسالب هو المهمّ:

| الحالة | النتيجة |
|---|---|
| قاعدة نظيفة (فيها «Default Company» وحدها) | ✅ البذر يمرّ — كان يُرفض قبل الإصلاح |
| قاعدة فيها شركة حقيقية | ✅ **ما زال يرفض**: «مرفوض: القاعدة تحوي شركات ليست من بيانات الحمل — #5 شركة حقيقية» |

الرسالة تسمّي الشركة الحقيقية **ولا تذكر الافتراضية** — أي أن الاستثناء جراحي
والحماية لم تُمَسّ.

### 5.3 ✅ P2-4 — تحقق الدخان أُنجز
