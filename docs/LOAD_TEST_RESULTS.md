## 0. لماذا لم تُقَس بعد

| العائق | التفصيل |
|---|---|
| **لا خادم تطبيقات يشبه الإنتاج على جهاز التطوير** | `gunicorn` غير مثبَّت، وهو **POSIX-only** (يستورد `fcntl`) فلا يعمل على Windows إطلاقاً. جهاز التطوير الحالي Windows 11. |
| **لا قاعدة MySQL معزولة** | القاعدة الوحيدة المهيّأة في `.env` هي **خادم الإنتاج**، وبرومت المرحلة 6 يمنع صراحةً تشغيل اختبار حمل ضد بيئة فيها بيانات مستخدمين حقيقيين. لم يُتّصل بها ولم يُقرأ منها ولم يُكتب فيها. |

**بدائل مرفوضة عمداً** (ولماذا):

- `waitress`/`runserver` بدل gunicorn ⇒ نموذج تزامن مختلف كلياً؛ الرقم الناتج لا يصف الإنتاج (سقف الإنتاج الفعلي = عدد workers الـgunicorn، وهو جوهر البند P0-1).
- SQLite بدل MySQL ⇒ لا تزامن كتابة حقيقياً، وخطط استعلام وفهارس مختلفة؛ كل ما يقيسه التدقيق (فهارس `StockMovement`/`JournalLine`، N+1، أقفال `select_for_update`) يختفي.
- تقدير الأرقام من قراءة الكود ⇒ ليس قياساً. التدقيق (`docs/SCALABILITY_AUDIT.md`) هو التحليل؛ هذا الملف مكانه القياس وحده.

**ما يلزم لإزالة العائق:** جهاز/حاوية Linux + MySQL فارغة اسمها يحوي `loadtest`، ثم تنفيذ §1 و§2 أدناه حرفياً.

## 1. تجهيز البيئة (مرة واحدة)

### 1.1 قاعدة بيانات معزولة

```bash
mysql -u root -p -e "CREATE DATABASE ktra_loadtest CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root -p -e "CREATE USER 'ktra_load'@'localhost' IDENTIFIED BY '<pw>'; \
                     GRANT ALL ON ktra_loadtest.* TO 'ktra_load'@'localhost';"
```

اسم القاعدة **يجب** أن يحوي `loadtest` — أمر البذر يرفض العمل بدونه (انظر §1.3).

بيئة التطبيق (ملف `.env` منفصل، لا تعديل على إعدادات الإنتاج):

```bash
export DB_NAME=ktra_loadtest DB_USER=ktra_load DB_PASSWORD='<pw>' DB_HOST=127.0.0.1
python manage.py migrate
```

### 1.2 اعتماديات مولّد الحمل (منفصلة عن الإنتاج)

```bash
python -m venv .venv-load
. .venv-load/bin/activate
pip install -r load_tests/requirements.txt      # locust==2.46.0
```

`load_tests/requirements.txt` منفصل عن `requirements.txt` الإنتاجي عمداً — لا يُثبَّت locust ولا gevent على الخادم.
النسخة 2.46.0 هي **آخر إصدار مستقر يقبل Python 3.10** (سقف السيرفر): 2.46.1 فما فوق يشترط `>=3.11` (مصدر التحقق: `https://pypi.org/pypi/locust/json`).

### 1.3 بذر بيانات بحجم واقعي

```bash
python manage.py seed_load_test_data --i-know-what-im-doing \
    --password '<كلمة مرور حسابات الحمل>' \
    --tenants 4 --products 800 --customers 200 --suppliers 40 \
    --invoices 1500 --days 540 --post-ratio 0.85 \
    --expect-db ktra_loadtest \
    --manifest load_tests/seed_manifest.json
```

يولّد لكل شركة: شجرة حسابات + فترات مالية + مستودع + ضريبة مخرجات 16% + أصنافاً برصيد افتتاحي حقيقي + عملاء وموردين + آلاف فواتير البيع **المرحّلة** (قيود وحركات مخزون فعلية). كل الكتابة تمرّ بمسارات النظام (`heal_company_seed`، `record_stock_movement`، `post_sales_invoice`، `next_invoice_number`) فما يُبذَر يطابق ما ينتجه النظام.

**حارس السلامة (5 طبقات، تسبق أي كتابة ويفشل مغلقاً):**

1. `--i-know-what-im-doing` إلزامي.
2. اسم القاعدة يحوي `loadtest`/`load_test`، أو يطابق `--expect-db` حرفياً.
3. **لا شركة في القاعدة خارج بادئة `LOADTEST`** — وجود شركة حقيقية واحدة يوقف الأمر.
4. **لا مستخدم غير مستخدمي الحمل** (عدا السوبر أدمن).
5. مضيف القاعدة محلي، إلا مع `--allow-remote-db` صراحةً. وSQLite مرفوضة إلا مع `--allow-sqlite` (أرقامها لا تمثّل الإنتاج).

الطبقتان 3 و4 هما الحارس الحقيقي: العَلَم يُنسى، أما قاعدةٌ فيها بيانات مستخدمين فتُوقف الأمر مهما بلغت الأعلام.

كلمة المرور تُمرَّر في سطر الأوامر ولا تُكتب في أي ملف — البيان (`seed_manifest.json`) يحمل معرّفات وبُرداً فقط، بلا أسرار.

### 1.4 تشغيل الخادم كما في الإنتاج

```bash
gunicorn core.wsgi:application \
    --bind 127.0.0.1:8000 \
    --workers "$((2 * $(nproc) + 1))" \
    --threads 4 \
    --worker-class gthread \
    --timeout 120 \
    --graceful-timeout 30 \
    --access-logfile - --error-logfile -
```

> ملاحظة تفسير: أمر النشر الحالي (`deploy.ps1:189-195`) هو `--workers 3` **sync بلا threads**، أي سقف مطلق = 3 طلبات متزامنة (P0-1). قِس **الحالتين**: إعداد النشر الحالي أولاً (خط الأساس الحقيقي)، ثم الإعداد أعلاه — الفرق بينهما هو أثر البند P0-1 وحده، وهو أرخص إصلاح في القائمة.

## 2. تشغيل التدرّج 50 → 150 → 300 → 500

```bash
export KTRA_LOADTEST_PASSWORD='<نفس كلمة مرور البذر>'
export KTRA_LOADTEST_MANIFEST=load_tests/seed_manifest.json

for U in 50 150 300 500; do
  locust -f load_tests/locustfile.py \
      --host http://127.0.0.1:8000 \
      --users "$U" --spawn-rate "$((U / 10))" --run-time 10m --headless \
      --csv "load_tests/results/run_${U}" --html "load_tests/results/run_${U}.html"
  sleep 120   # تهدئة بين المستويات كي لا يتداخل ذيل مستوى بأوّل الذي يليه
done
```

**الخليط المرجّح في `load_tests/locustfile.py`** (مطابق لبرومت المرحلة 6):

| الوزن | السلوك | النقاط الفعلية |
|---|---|---|
| 40% | فتح قوائم | `/api/sales/invoices/?page` · `/api/inventory/products/?page` · `/api/partners/?page` · `/api/accounting/journals/?page` · `/api/inventory/stock-movements/?page` · `/api/logistics/purchase-invoices/?page` |
| 25% | تفاصيل مستند | `/api/sales/invoices/{id}/` (وجزء منها فحص عزل — أدناه) |
| 15% | إنشاء فاتورة بيع كاملة | `POST /api/sales/invoices/` (2-5 بنود) ثم `POST /api/sales/invoices/{id}/post/` |
| 10% | تقرير | `/api/reports/{sales-summary\|sales-by-customer\|sales-invoices\|receivables-aging\|payables-aging\|stock-valuation\|customer-balances}/` |
| 10% | بحث/autocomplete | `/api/inventory/products/?view=lookup&search=` · `/api/partners/lookup/?search=` |

**تفاصيل تعاقدية روعِيَت في السيناريو:**

- **العزل عبر `X-Tenant-Id`:** كل مستخدم افتراضي مربوط بشركة واحدة طوال حياته، وموزَّع بالتناوب على 3-5 شركات. `core/tenant_utils.py:33-45` لا يستنتج الشركة إلا حين تكون وحيدة في القاعدة — وهو ما لا يصحّ هنا عمداً.
- **الترقيم إلزامي بعد P0-5:** قوائم الفئة أ على `EnforcedPageNumberPagination`؛ كل طلب قائمة يمرّر `?page=&page_size=`. طلبات الـautocomplete وحدها بلا ترقيم لأنها المسار الفعلي للمحدِّدات (`view=lookup` / `lookup/`).
- **حدّ محاولات الدخول (P0-13):** `hr/auth_api.py:171` يحدّ 10 إخفاقات لكل بريد/IP كل 15 دقيقة. لذلك **التوكن يُجلَب مرة واحدة لكل حساب ويُشارَك** بين كل المستخدمين الافتراضيين عليه — 500 مستخدم افتراضي = 3-5 عمليات دخول لا 500.
- **حدود الخطة:** شركات البذر على خطة `Enterprise` (بلا حدود، `core/plans.py`) — وإلا رُفضت فواتير الحمل بـ«تجاوزت حدّ الخطة» فبدا الرفض خطأ أداء.

**فحص العزل تحت الحمل (لا الأداء وحده):** نسبة `KTRA_LOADTEST_ISOLATION_RATIO` (افتراضياً 10%) من طلبات التفاصيل تستهدف **مستند شركة أخرى** بتوكن شركةٍ أخرى. الردّ المقبول 403/404؛ أي `200` يُسجَّل فشلاً باسم `[isolation]` في تقرير locust. أي رقم غير صفر في هذا السطر = خرق عزل تحت التزامن ويسبق كل نقاش أداء.

## 4. قرار Celery

> ### ⏸️ القرار **معلَّق على القياس** — لم يُتَّخذ
> برومت المرحلة 6 يشترط أن يُبنى القرار على «endpoints تتجاوز 3-5 ثوانٍ تحت
> الحمل بسبب عمل ثقيل داخل دورة الطلب». هذا الشرط **يحتاج قياساً**، والقياس لم
> يجرِ. لذلك لا يصحّ هنا أيٌّ من الحكمين: لا «Celery مطلوب» ولا «Celery غير
> مطلوب عند هذا الحجم» — كلاهما بلا أرقام يكون ادّعاءً لا قراراً.
>
> **الحالة الراهنة (حقيقة لا قرار):** لا celery ولا redis ولا أي task queue في
> `requirements.txt` (`SCALABILITY_AUDIT.md §1.2`) — كل عمل ثقيل داخل دورة الطلب.

### 4.1 المرشّحون — قائمة جاهزة للحكم عليها بالقياس

مصدرها `docs/SCALABILITY_AUDIT.md §6 «مرشّحو Celery»` + بندا P1-12 وP1-13 من جدول P1.

> تنبيه مسارات: مراجع `logistics/views.py` و`core/reports.py` أدناه منقولة كما وردت
> في التدقيق؛ بعد المرحلة 3 صار الملفان **حزمتين** (`logistics/views/` و`core/reports/`)
> بنفس الموضع وبنفس الأسماء العامّة — فابحث عن الدالّة داخل وحدة الدومين المناسبة.

| # | المرشّح | الموضع | لماذا مرشَّح | كيف يُقاس (النقطة التي تكشفه) |

### 4.2 قاعدة القرار (تُطبَّق حرفياً بعد القياس)

1. مرشَّح p95 ≥ 5s تحت 500 مستخدم ⇒ **نقلٌ إلى Celery** (أو إعادة تصميم إن كان السبب أقفالاً لا طول عمل — حالة C3 تحديداً: طابور المهام لا يحلّ تنازع الأقفال، بل يؤجّله).
2. 3s ≤ p95 < 5s ⇒ مرشَّح من الدرجة الثانية؛ جرّب أولاً الكاش/الاستعلام (أرخص وأقل أثراً معمارياً).
3. p95 < 3s على كل المرشّحين ⇒ **يُوثَّق صراحةً «Celery غير مطلوب عند هذا الحجم»** مع الجدول الذي يدعم ذلك.
4. أياً كان الحكم: Celery **لا يُنفَّذ في المرحلة 6** — القرار والتوثيق فقط (قيد صريح في البرومت).

### 4.3 تبعية مسبقة

Celery يفترض وسيطاً (Redis غالباً). البند P0-6 (استبدال `FileBasedCache`) موسوم منفَّذاً في `SCALABILITY_AUDIT.md`، لكن التشغيل الفعلي على الخادم المشترك بلا Redis يجعل هذه التبعية **جزءاً من كلفة القرار لا هامشاً منه**: أي «نعم لـCelery» يعني أولاً وسيط رسائل مُدارٌ في الإنتاج.
